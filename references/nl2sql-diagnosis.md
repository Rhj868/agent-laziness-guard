# 场景二：NL2SQL 只对调试过的问题有效

## 现象

问题一的 SQL 经用户反馈后被修正并执行成功，但同类问题二仍生成错误 SQL。

仅凭「新问题又错了」不能确定是模型照抄历史 SQL。应以证据区分理解错误、元数据不足、生成错误与执行环境错误。

## 五类可能原因

- Schema、字段注释或关系信息不完整。
- 业务口径、时间范围、去重规则等没有定义清楚。
- 当前问题被误解，或历史 SQL 被不恰当地当作模板。
- 生成的 SQL 没有经过语法、权限和结果检查。
- 用户反馈只修正了当前查询，未被整理成清晰、经确认的通用规则。

## 每个新问题必须留存的证据

| 字段 | 用途 |
| --- | --- |
| 当前问题原文 | 判断是否被误解、是否套用了历史模板 |
| Schema 版本 | 排除元数据变更与信息缺失 |
| 生成的 SQL | 复现与比对 |
| 执行错误 | 区分生成错误与执行环境错误 |
| 校验结果 | 确认是否真正做过语法、字段、权限、成本检查 |

## 改进原则

每个新问题都以**本轮需求、可用 Schema 和已确认的业务规则**为主要依据。历史查询可作为示例，但不得替代对当前需求的理解。

只有确认某条规则具有通用性后，才将其写入业务字典、规则库或测试用例；单次纠错不应自动变成全局规范。

## 生成与校验七条规则

1. **解析用户需求**：明确指标、维度、时间范围、过滤条件、排序和结果粒度；对影响结果的歧义先澄清。
2. **核对元数据**：确认表、字段、类型、关联键、枚举值及业务定义均存在且适用于当前问题。
3. **生成 SQL**：按当前需求独立组织查询逻辑。可复用经过确认的规则或模板，但不得仅因历史 SQL 成功就机械套用。
4. **执行前校验**：检查 SQL 方言与语法、字段和表是否存在、JOIN 是否可能造成重复、聚合粒度是否正确、时间边界是否符合口径。
5. **安全执行**：通过只读账号、查询超时、资源限制和允许语句检查等工程措施落实权限。提示词中的「只生成 SELECT」不能替代数据库权限控制。
6. **处理反馈**：先分类错误原因，再修正当前查询。只有确认可泛化的规则才写入规则库，并补充正反例测试。
7. **说明结果**：可给出简短的查询逻辑说明、所用表字段和口径假设；不要求模型披露隐藏的逐步思维过程。简短说明也不能代替实际校验。

## 五层工程结构

| 层 | 职责 |
| --- | --- |
| 元数据层 | 维护版本化 Schema、字段注释、关系和业务口径 |
| 生成层 | 输入当前问题及必要元数据，生成候选 SQL |
| 校验层 | 独立检查语法、字段、权限、查询成本和业务规则；必要时在只读环境执行 |
| 反馈层 | 记录错误类型及修复结果；经人工或规则流程确认后，再更新元数据、规则或回归测试 |
| 评估层 | 使用覆盖不同表、条件、聚合和时间边界的测试集，避免只验证被修正的单条问题 |

## 关于双 Agent

双 Agent 并非必需。若采用生成器与校验器分离，应确保校验器有明确规则和**工具证据**；增加 Agent 数量本身不保证正确性。

## 反馈分类口径

将用户反馈归入以下之一，再决定修复动作：

| 类别 | 典型修复 |
| --- | --- |
| 需求理解 | 澄清歧义，重写问题解析 |
| 元数据 | 补全 Schema、字段说明、关联关系 |
| 业务口径 | 定义并确认指标、时间范围、去重规则 |
| SQL 生成 | 修正查询逻辑，不得机械套用历史 SQL |
| 执行环境 | 处理权限、超时、方言差异、资源限制 |

## 回归要求

测试集至少更换：表、时间范围、过滤条件、聚合方式。记录通过率、失败类别和未覆盖范围；只验证被修正的单条问题不算修复完成。
