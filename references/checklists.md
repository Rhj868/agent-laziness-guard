# 验收清单、证据信号与落地路径

## 共同结论

两类典型问题都需要把输入边界、状态流转和验证证据设计清楚，但根因可能不同：

- 文件场景重点检查「当前文件是否被正确读取」。
- NL2SQL 场景重点检查「当前需求是否被正确映射并通过校验」。

可靠的改进路径：

1. 明确本轮任务输入和允许使用的历史信息。
2. 记录工具调用、输入标识及返回状态。
3. 将通用规则与单次样例分开管理。
4. 对关键输出进行可重复的验证。
5. 用多样化回归用例确认修复有效。

「要求模型重新推导」或「让模型自检」可以作为辅助提示，不能单独证明结果可靠。

## 项目任务通用执行与验收流程（详版）

| 步骤 | 动作 | 产出 |
| --- | --- | --- |
| 1 需求拆解 | 将用户请求转为验收清单，记录输入、输出、限制条件和明确不在范围内的事项；隐含要求一并纳入 | 可逐项打勾的验收清单 |
| 2 项目理解 | 检查相关说明、代码、配置、依赖和当前工作区状态，确认改动位置及潜在影响 | 改动位置清单、影响面说明 |
| 3 方案与假设 | 识别不确定点和高风险路径；低风险细节可采用合理默认值，但记录可能影响结果的假设 | 假设清单（含影响判断） |
| 4 执行留痕 | 对文件读取、命令执行、外部工具调用和数据变更保留可核对结果；区分「准备执行」「已执行」「执行失败」 | 命令输出、工具返回、diff |
| 5 分层验证 | 先验证改动本身，再验证相关集成和用户验收项；测试范围与风险相匹配。未获请求时不扩大到无关测试或改动 | 运行命令、通过数、失败数、失败归因 |
| 6 差异复核 | 检查最终变更是否对应需求，是否有意外文件、未处理错误、泄露信息或未说明的行为变化 | diff 复核记录 |
| 7 如实交付 | 总结改动、证据、未验证部分和限制；任何未完成的验收项都明确列出 | 交付说明 |

### 四类状态定义

为关键步骤显式区分：

- **成功**：返回码正常、必要字段齐全、数据完整。
- **部分成功**：结果不完整或缺失非关键字段，需标注缺失范围后再决定是否可用。
- **失败**：工具报错、校验不通过、结果为空。停止依赖该结果的后续步骤。
- **超时**：达到时限且无有效结果，不得按空结果静默处理。

## 识别「偷懒」的证据信号

出现以下情况时，应进一步检查执行过程，而不是仅凭措辞判断：

- 验收项没有逐项对应结果或证据。
- 结论声称已读取、运行、修改或部署，但没有工具记录或产物。
- 只验证一个样例，未覆盖用户给出的其他条件或失败路径。
- 实现依赖硬编码、静默降级、吞异常或未说明的假设。
- 改动与需求无关，或工作区中原有改动被覆盖。
- 测试失败、工具报错或结果不完整，却仍被报告为成功。

以上信号用于定位流程缺口，**不等于单独证明模型「偷懒」**。改进应优先让任务可检查、工具状态可观察、验证可重复，并让未完成状态如实暴露。

## 落地清单（9 项）

第一阶段——先补齐可观测性（优先级最高）：

1. 为文件任务记录本轮文件 ID、解析状态、解析内容长度及检索片段来源。
2. 在新文件到达时更新任务状态；对并发任务使用独立状态，避免跨任务串线。
3. 对解析失败、空结果和检索无召回设置明确错误分支。
4. 将用户反馈分类为理解、元数据、业务口径、SQL 生成或执行环境问题。

第二阶段——完善元数据与校验：

5. 为 NL2SQL 补全 Schema、字段说明、关联关系及经确认的业务口径。
6. 在数据库侧使用只读权限、超时和资源限制；执行前增加语法及权限检查。
7. 通用规则经确认后才写入规则库，并配套正反例测试；单次修复不自动升级为通用规则。

第三阶段——持续验证：

8. 每次修改后运行覆盖多个输入的回归测试。文件测试至少更换文件类型或内容；SQL 测试至少更换表、时间范围、过滤条件及聚合方式。
9. 记录通过率、失败类别和未覆盖范围。单个样例成功不等于问题已解决。

实施顺序：先补齐日志、状态传递和错误分支，再完善元数据与校验。提示词适合表达意图；可靠性应由可观察的工具结果、工程约束和回归测试共同支持。

## 交付说明结构

1. **改动范围**：涉及的文件/模块，附具体位置。
2. **验证结果**：运行了什么、命令与输出、通过数与失败数。
3. **验收项对照**：逐项标注「已完成（证据）」或「未完成（原因）」。
4. **未验证部分与已知限制**：明确列出，不用「基本完成」掩盖。
5. **假设**：记录可能影响结果的假设。
6. **产物链接**：构建产物、报告、代码位置。
